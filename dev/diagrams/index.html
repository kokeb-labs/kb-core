Figures¶

Every figure on this site is drawn by a Python module from facts extracted from the code, so it is rebuilt, not redrawn, when the code changes. CI runs kokeb-docs figures --check and fails when a committed figure no longer matches the code. Each figure below lists the files it is drawn from.

From tags to a project¶

Figure description and sources

Left to right. kb catalog build reads each driver's driver.yml at its tags and the kb-core tags with their platform table and pins, and writes catalog.json. The resolver, one specification with a Python and a JavaScript implementation, reads kb-image.yml and the catalogue and writes the lock kb-image.lock.yml and three project files: CMakePresets.json, kb_image.cmake and kb-fetch.sh. kb sbom turns the lock into CycloneDX 1.6 and SPDX 2.3 documents.

One asynchronous read¶

Figure description and sources

The owner task starts the transfer in one service pass and collects the result in a later one; no pass waits. AsyncPoller owns the buffers and asks the port to start; a Poll in the next pass reports Pending until the peripheral interrupt has set the owner's event flag and the transfer is complete, then Done with the count. Past the deadline the result is Done with Timeout, late data included; Cancel makes the poller Idle and releases the buffers.

Figure module: docs/diagrams/figures/async-poll.py

Held transactions¶

Figure description and sources

On a guarded bus a task takes the handler mutex first and then the bus mutex, both bounded, and holds the bus for several calls with nothing in between; another task's plain request waits (bounded) or times out. On an owner bus the owner task takes the hold between passes, which never waits, and runs inline calls for several handlers; the service pass reports Busy while the hold is held and the violation is counted.

Figure module: docs/diagrams/figures/bus-hold.py

One call through the layers¶

Figure description and sources

A HAL reads a register of a PF1550 power IC. The HAL calls the guarded handler (its bus is declared guarded), which takes the handler lock and then the bus lock, both bounded, and calls the driver. The driver calls its own WriteRead hook, implemented by the kb binding, which calls the ESP32 I2C device of the port. The port answers ok or an I2cFailure (AddressNack, DataNack, Bus, Timeout, BusStuck); the binding returns a bool and keeps the failure for GetLastFailure; the driver returns its Result; the handler returns a kb::Result carrying the driver's error in detail. Only the last step knows it runs on an ESP32.

Figure module: docs/diagrams/figures/call-sequence.py

The CI flow¶

Figure description and sources

From the left. Every change first passes tools/preflight.sh on a workstation, then reaches CI as a pull request or push. Always run: repository checks, layering, layout and examples, own parts, MISRA and pin hygiene. Run when the paths match, and on main and tags: quality, integration, the ESP-IDF port job and the catalogue. Never re-run for components/drivers: the drivers' own tests, which are trusted through pin hygiene. Everything ends in one required gate; a tag adds the release assets, and a schedule re-scans releases for known vulnerabilities.

Parts, ports and drivers¶

Figure description and sources

Three bands read from the folders of the repository, so the figure cannot drift. components/lib holds the parts: kb::utils at the bottom, kb::rtos on it, kb::interfaces on that, and kb::handlers on top. components/ports holds the MCU ports, which satisfy the interface contracts (the host port is for tests). components/drivers holds the pinned drivers, each a submodule at a release tag; kb::handlers binds them and nothing else may use them.

Which layer may depend on which¶

Figure description and sources

Two columns. On the left, the allowed dependencies: the application uses the board HAL, kb::rtos and kb::utils; the board HAL uses kb::handlers, kb::interfaces and one MCU port; the MCU port uses installed interface headers and, in boundary files, the vendor SDK; handlers use drivers and interfaces; interfaces use kb::rtos; kb::rtos uses kb::utils. Ownership of a DMA buffer¶

Figure description and sources

Three states. A buffer is constructed in Cpu: static, line-aligned and padded. Lend moves it from Cpu to Device after the owned cache lines are cleaned or invalidated and a barrier ran. Complete moves it from Device back to Cpu after a receive is invalidated and a barrier ran. Abort with proof that the bus master stopped also returns it to Cpu. Abort without proof, or a lease destroyed while the device owns the buffer, moves it from Device to Quarantined. Recover with proof, after the peripheral was re-initialised, moves it from Quarantined to Cpu. In Quarantined a Lend is refused with a Fault and the CPU view is empty. Only the port holds the key that moves a buffer between states (ADR-0030).

Figure module: docs/diagrams/figures/dma-lease.py

The DMA copy-out stream¶

Figure description and sources

Two rows of three steps. The DMA ring in the buffer holds two halves or N frames. A half or complete interrupt makes PublishFromDevice invalidate the lines, copy the finished frame out and stamp a sequence number, a time and a torn flag. It copies into a slot of a ring of at least two slots; when every slot is held the frame is dropped, counted as Full, and the next frame carries Gap(). The task takes a slot with TryTake and reads it through a move-only FrameView that releases on its end. Judge checks the content, and Supervise answers None, Restart, BackOff or UseFallback. EnterFallback switches to the declared fallback producer, whose frames carry Fallback(). The ring is never lent to the task (ADR-0031).

Figure module: docs/diagrams/figures/dma-stream.py

Fault evidence path¶

Figure description and sources

Handler health is read lock-free and only its edges go to the HealthJournal. The LivenessMonitor's verdict goes there too, and the watchdog owner is kicked only when nothing is stale. The journal appends with one bounded store write into a FaultJournal ring of 32-byte CRC-32 records with a sequence number; at boot the port's reset reason is recorded. The store (RTC or no-init RAM, NVS, FRAM, flash) belongs to the port; after a reset Open() finds the newest record and skips a torn slot.

Figure module: docs/diagrams/figures/fault-journal.py

Generators and the configurator¶

Figure description and sources

Left to right. Inputs are single sources published with each kb-core release: each pinned driver's driver.yml, the release lock with its tags and SHAs, the evidence (SBOM, CVE scan, licence report), the tested version sets and, later, board.yml. One resolver specification has two front ends, the kb command line and the static configurator site; it resolves drivers to handlers to interfaces to parts, applies the MCU gates, kb_core_min and the thread model per bus. It produces byte-for-byte repeatable downloads: kb-image.yml, git commands, a CMake presets fragment with kb_image.cmake, the evidence for the selection and, later, a project archive.

Handler lifecycle and health¶

Figure description and sources

Seven states. A handler starts Unknown (constructed, no I/O). EnsureInitialized or StartStep moves it to Starting, which walks the declared stages, each bounded by its deadline; the last stage makes it Ready. A failing call makes a Ready handler Degraded until the next call succeeds; fault_after failures in a row, or one fatal error (the chip reset or lost its state), make it Faulted. Recover() moves Faulted to Recovering with a backoff that doubles on each failure and is refused after max_attempts. Deinitialize() returns Ready or Faulted to Unknown. Only EnsureInitialized, StartStep, Deinitialize and Recover change the lifecycle: calls never start or restart the chip.

Figure module: docs/diagrams/figures/handler-health.py

The pieces of a handler¶

Figure description and sources

Top to bottom. A HAL manager or application task calls an access facade with EnsureStarted, Request, Sample, Latest or Health; there is one facade per handler, chosen by the bus's thread model: OwnerAccess (request queue and a lock-free snapshot) or Guarded (handler lock, then bus lock). Only a facade can make the ServiceKey that the handler core needs. The core, HandlerCore of the handler, the driver, the snapshot, the command and the reply, holds the start-up plan runner, the health record, the snapshot and a liveness beat. It builds the driver in a std::optional; the driver reaches the bus through the binding's Port, hooks over the kb::iface contract that the HAL supplies. The facade also owns the BusDomain of its bus.

Figure module: docs/diagrams/figures/handler-pieces.py

The handler start-up pipeline¶

Figure description and sources

One runner and a declared plan of stages per chip, in a fixed order: Power, HostReset, Boot, Link, Identify, Secure, Configure, Verify, then Ready. A plan lists only the stages its chip needs; an optional stage is skipped when the HAL supplies no pin, rail or key for it. Every stage is synchronous or polled, and bounded by a deadline. Most drivers declare one step that calls the driver's EnsureInitialized. The bno08x resets and boots with polled steps; the se05x sets platform keys, opens the secure link and optionally checks the lifecycle state.

Figure module: docs/diagrams/figures/handler-startup.py

Handler thread models¶

Figure description and sources

Two models, declared per bus; callers on other tasks use one access API in both. In the owner-task model, one real-time task calls Service(now) at a fixed rate, steps the single-threaded handlers on a bus domain without a mutex, publishes each step to a lock-free seqlock snapshot and drains a bounded command queue. Other tasks read the latest snapshot (a lock-free copy) or post a request and wait with a timeout. In the guarded model, each calling task takes the handler lock and then, within a bounded wait, the bus lock of a mutex-protected bus domain. An interrupt service routine only sets event flags or notifies the owner task.

Figure module: docs/diagrams/figures/handler-threading.py

The layer stack¶

Figure description and sources

From top to bottom. The product application calls the board HAL. The board HAL talks to kb::handlers and picks one MCU port; handlers use the driver of each chip and the interface contracts, the contracts rest on kb::rtos, and kb::rtos rests on kb::utils. The MCU port satisfies the interface contracts and touches the vendor SDK in its boundary files only; the RTOS backends touch the kernel in theirs. The vendor SDK, kernels and mbedTLS are SOUP: never analysed, never edited.

Figure module: docs/diagrams/figures/layer-stack.py

MISRA C++:2023 scope¶

Figure description and sources

Four zones, from strongest claim to none. kb-core's own code under components/lib is claimed compliant with zero repository deviations: utils, interface contracts and host port, the rtos public API, and handlers with bindings. Boundary files, the RTOS backends' and the ports' files that touch vendor code, are compliant with recorded deviations. Each driver at its pinned tag is covered by its own MISRA run at level high. SOUP (ESP-IDF, STM32 HAL, FreeRTOS, ThreadX, mbedTLS) is out of scope, listed with versions, included with -isystem and never reported.

Figure module: docs/diagrams/figures/misra-scope.py

The kb repository family¶

Figure description and sources

Five levels, consumers on top. A product organisation owns the product application and its board HAL. The kokeb-labs organisation holds kb-core (utils, rtos, interfaces, handlers and the driver pins), kb-hal-common (shared HAL bases), the reference board HALs and, planned, the configurator, an application template and tested version sets. The kokeb-labs-drivers organisation holds each driver and each MCU port. The board HAL builds on kb-hal-common and one port; both rest on kb-core, which pins the drivers. The configurator reads kb-core releases and fills the application template. Only kb-core exists today; the other names are planned.

Figure module: docs/diagrams/figures/repo-family.py

Phase roadmap¶

Figure description and sources

Eight phases, M0 to M7, in order; there are no calendar dates, each phase ends on its exit criteria. M0 fixes decisions and guardrails. M1 to M3 deliver kb::utils, kb::rtos and kb::interfaces, each with MISRA zero findings, the coverage floor, the mutation gate and fuzzing. M4 adds the ESP32 port and the first bindings. M5 rolls out handlers for all drivers, simplest to hardest. M6 adds breadth: a second port, the ThreadX backend, tested version sets and release evidence in the configurator. M7 adds the generators: pin tables from board.yml, a project archive and HIL in CI.

Figure module: docs/diagrams/figures/roadmap.py

kb::rtos backends¶

Figure description and sources

One API, one seam, four backends. The kb::rtos API (components/lib/rtos/inc) reaches a backend through kb::rtos::backend (backend.hpp). The none backend is for host tests and bare-metal bring-up; FreeRTOS and ThreadX each have boundary files that reach the kernel, which is SOUP, either a product's copy or the pinned or ESP-IDF one; the host backend (std::thread) is for tests only. FreeRTOS and ThreadX tests run against a fake kernel.

Figure module: docs/diagrams/figures/rtos-backends.py

The ThreadX backend¶

Figure description and sources

The kb::rtos API reaches the seam, kb::rtos::backend. The ThreadX backend is two files: threadx_isr.cpp, where every FromIsr call is the same call with TX_NO_WAIT, and threadx_boundary.cpp, the only boundary file, which creates ThreadX objects on kb-owned control blocks and stacks. The kernel is SOUP and never edited; it comes from a product's copy (KB_THREADX_INCLUDE_DIRS, for STM32Cube or a vendor SDK) or from the pinned submodule third_party/threadx at a release tag, with KB_THREADX_PORT choosing cortex_m0, cortex_m4, cortex_m7 or linux. Tests run the boundary on a fake kernel (contract and seam, exact ticks) and, on the pinned kernel's Linux port, as a threaded suite with priority inheritance.

Figure module: docs/diagrams/figures/rtos-threadx.py

The update path¶

Figure description and sources

Left to right. kb outdated, or the configurator's Open an existing project view, plans from the current lock, the catalogue and the image: kb-core moves first, then an extracted port, then each driver in name order. Each candidate must pass the driver gates in order (MCU family, kb_core_min, owner-task rule, bus kind in use); a newer version that fails is held back with the code of its first failing gate. The plan lists one row per component with the SemVer change, whether it breaks, and known vulnerabilities fixed and remaining. kb upgrade writes a new image and lock, the CMake files, the fetch script and kb-upgrade.md; the user reviews the diff and runs the fetch script, builds and tests.
