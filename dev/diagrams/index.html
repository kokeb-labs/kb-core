    Figures¶

    Every figure on this site is drawn by a Python module from facts extracted from the code, so it is rebuilt, not redrawn, when the code changes. CI runs kokeb-docs figures --check and fails when a committed figure no longer matches the code. Each figure below lists the files it is drawn from.

    From tags to a project¶

    Figure description and sources

    From the top. kb catalog build reads each driver's driver.yml at its tags and the kb-core tags with their platform table and pins, and writes catalog.json, every part at every version. The resolver, one specification with a Python and a JavaScript implementation, reads kb-image.yml (what the user selected) and the catalogue, and writes the lock kb-image.lock.yml (every version, tag and SHA) and three project files: CMakePresets.json, kb_image.cmake and kb-fetch.sh. kb sbom turns the lock into CycloneDX 1.6 and SPDX 2.3 documents.

    One asynchronous read¶

    Figure description and sources

    The Owner task starts the transfer in one service pass and collects the result in a later one; no pass waits. In pass n the Owner task calls StartWriteRead on the AsyncPoller, which owns the buffers and asks the Port (I2cAsync or SpiAsync) to start with a deadline; the port answers Ok at once. A Step(now) in the same pass makes the poller call Poll(now), which reports Pending. The peripheral ISR then finishes the transfer and sets the owner's event flag. In pass n+1 the poll reports Done, Ok with the count, and Completion() is Ok with the bytes held. Past the deadline the result is Done with Timeout, late data included; Cancel() makes the poller Idle and releases the buffers.

    Held transactions¶

    Figure description and sources

    Guarded bus, on the left: task X calls Guarded::Hold(timeout), takes the handler mutex first and then the bus mutex through BusDomain::Hold, both with a bounded wait, and holds the bus in GuardedHeld for several calls (Request, Sample and so on) with nothing in between; another task's plain Request waits (bounded) or returns Timeout. Owner bus, on the right: the owner task takes BusDomain::Hold() between passes, which never waits, and sets the pass flag while the hold is held; OwnerAccess::Held(hold) runs inline calls for several handlers, and Service(now, ...) reports Busy while the hold is held and the violation is counted.

    One call through the layers¶

    Figure description and sources

    A HAL reads a register of a PF1550 power IC; solid arrows are calls, going down, and dashed arrows are returns, going up. The HAL calls the guarded handler with Call(timeout, ReadRegister) (its bus is declared guarded), which takes the handler lock and then the bus lock, both bounded, and calls the driver. The driver calls its own WriteRead hook, WriteRead(addr, tx, n, rx, m), implemented by the kb binding (Pf1550Port), which calls WriteRead(addr, span, span) on the ESP32 I2cDevice of the port. The port answers ok or an I2cFailure (AddressNack, DataNack, Bus, Timeout, BusStuck); the binding returns a bool and keeps the failure for GetLastFailure; the driver returns its Result; the handler returns a kb::Result carrying the driver's error in detail. Only the last step knows it runs on an ESP32.

    The CI flow¶

    Figure description and sources

    From the top. Every change first passes tools/preflight.sh on a workstation, then reaches CI as a pull request or push. Always run: repository checks (DCO, lint, handbook, drift), layering (include checker, CMake DAG, poison build, symbol lint), layout and examples (root allowlist, retired locations, example index), own parts (host build and tests on GCC and Clang, clang-tidy, cppcheck), MISRA at level high (CodeQL pack plus kokeb-cpp20, host and Cortex-M) and pin hygiene (gitlink, lock and a release or rc tag with a green gate, never a branch). Run when the paths under components/drivers, handlers, interfaces, ports or cmake match, and on main and tags: quality (coverage, sanitizers, fuzz, mutation kill-rate gate), integration (the binding, port, MCU and RTOS matrix from catalog/compat.yml), the ESP-IDF v5.5 build of the port and the catalogue (regenerate compat.yml, fail on drift). Never re-run for components/drivers: the drivers' own tests, fuzz, mutation, MISRA, tidy and docs, which each driver runs in its own repository and which are trusted through pin hygiene. Everything ends in one required gate, ru-ci-gate; a tag vX.Y.Z adds the release assets (per-part packages, SHA256SUMS, compat.yml, release lock, SBOM, CVE scan, licence report, provenance), and a schedule re-scans releases for known vulnerabilities and records the tested version set kb YYYY.N.

    Parts, ports and drivers¶

    Figure description and sources

    Read from the folders of the repository, so the figure cannot drift.     Which layer may depend on which¶

    Figure description and sources

    The twelve allowed dependencies come first: the application uses the board HAL, kb::rtos and kb::utils; the board HAL uses kb::handlers, kb::interfaces and one MCU port; the MCU port uses the installed kb::interfaces headers only and the vendor SDK headers in boundary files only; kb::handlers uses the drivers and kb::interfaces; kb::interfaces uses kb::rtos; kb::rtos uses kb::utils. The seven forbidden dependencies follow, each with the check that catches it: the application using kb::interfaces or the SDK directly (the include checker and the symbol lint), kb::handlers using the SDK (the poison build and the include checker) or an MCU port (the CMake DAG check), kb::interfaces using an MCU port (the include checker, LAY-010), a driver using kb::utils (the driver CI and the include checker), and kb::utils using kb::rtos (the CMake target graph). Each cell carries a word and a mark, so the meaning does not rest on colour alone.

    Ownership of a DMA buffer¶

    Figure description and sources

    Three states. A buffer is constructed in Cpu: static, line-aligned and padded. Lend moves it from Cpu to Device after the owned cache lines are cleaned or invalidated and a barrier ran. Complete moves it from Device back to Cpu after a receive is invalidated and a barrier ran; Abort with proof that the bus master stopped also returns it to Cpu. Abort without proof, or a lease destroyed while the device owns the buffer, moves it from Device to Quarantined. Recover with proof, after the peripheral was re-initialised, moves it from Quarantined to Cpu. In Quarantined a Lend is refused with a Fault and the CPU view is empty. Only the port holds the key that moves a buffer between states (ADR-0030).

    The DMA copy-out stream¶

    Figure description and sources

    From the top. The DMA ring in the buffer holds two halves or N frames. A half or complete interrupt makes PublishFromDevice invalidate the lines, copy the finished frame out and stamp a sequence number, a time and a torn flag. It copies into a slot of a ring of at least two slots; when every slot is held the frame is dropped, counted as Full, and the next frame carries Gap(). The task takes a slot with TryTake and reads it through a move-only FrameView that releases on its end. Judge checks the content, and Supervise answers None, Restart, BackOff or UseFallback. EnterFallback switches to the declared fallback producer, whose frames carry Fallback(). The ring is never lent to the task (ADR-0031).

    Fault evidence path¶

    Figure description and sources

    Handler health is read lock-free and only its edges go to the HealthJournal. The LivenessMonitor's verdict goes there too, and the watchdog owner is kicked only when nothing is stale. The journal appends with one bounded store write into a FaultJournal ring of 32-byte CRC-32 records with a sequence number; at boot the port's reset reason is recorded with RecordReset. The store (RTC or no-init RAM, NVS, FRAM, flash) belongs to the port; after a reset Open() finds the newest record and skips a torn slot.

    Generators and the configurator¶

    Figure description and sources

    From the top. Inputs are single sources published with each kb-core release: each pinned driver's driver.yml (bus, mcus, peripheral, kb_core_min, ports, binding), the release lock with the kb-core tag and SHA and every pin with its tag and SHA, the evidence (SBOM in SPDX and CycloneDX, CVE scan, licence report), the tested version sets kb YYYY.N and, later, board.yml with buses, pins and chips. One resolver specification has two front ends, the kb command line (Python standard library only, tools/kb) and the static configurator site on GitHub Pages, where the user picks MCU, RTOS, drivers and handlers. It resolves drivers, then handlers, interfaces and parts, and applies the MCU gates, kb_core_min and the thread model per bus. It produces byte-for-byte repeatable downloads: kb-image.yml (the selection), git commands (clone at the tag, check the SHA, init only the enabled submodules), a CMake presets fragment with kb_image.cmake, the evidence for the selection (SBOM, CVEs, licences, compatibility rows, tested set) and, later, a project archive.

    Handler lifecycle and health¶

    Figure description and sources

    Six states. A handler starts Unknown (constructed, no I/O). EnsureInitialized or StartStep moves it to Starting, which walks the declared stages, each bounded by its deadline; the last stage makes it Ready, a failing stage makes it Faulted, and a failed start leaves the driver destroyed so the next start begins again from the first stage. A failing call makes a Ready handler Degraded until the next call succeeds; fault_after failures in a row, or one fatal error (the chip reset or lost its state), make it Faulted. Recover() moves Faulted to Recovering with a backoff that doubles on each failure, and is refused after max_attempts; Recovering returns to Ready when the plan succeeds and to Faulted when it fails. Deinitialize() returns Ready or Faulted to Unknown. Only EnsureInitialized, StartStep, Deinitialize and Recover change the lifecycle: calls never start or restart the chip.

    The pieces of a handler¶

    Figure description and sources

    From the top. A HAL manager or application task calls an access facade with EnsureStarted, Request, Sample, Latest or Health; there is one facade per handler, chosen by the bus's thread model: OwnerAccess (request queue and a lock-free snapshot) or Guarded (handler lock, then bus lock). Only a facade can make the ServiceKey that the handler core needs, and the facade also owns the BusDomain of its bus, which holds one bus and its declared thread model. The core, HandlerCore of the handler, the driver, the snapshot, the command and the reply, holds the start-up plan runner (kStartupPlan), the health record and the snapshot (both seqlocks) and a liveness beat. It builds the driver in a std::optional; the driver reaches the bus through the binding's Port, driver hooks (I2cHooks, SpiHooks, UartHooks, AdcHooks, GpioHooks) over the kb::iface contract through which the HAL supplies its bus, pins and clock.

    The handler start-up pipeline¶

    Figure description and sources

    Two columns. Stages, in order: one runner and a declared plan of stages per chip, in a fixed order: Power (rail or enable pin), HostReset (reset pulse, hold, release), Boot (boot time, ready pin, advertisement), Link (transport session, T=1 or SHTP), Identify (ID, select, probe, capabilities), Secure (secure channel, platform SCP03), Configure (apply the configuration), Verify (read-back, lifecycle state), then Ready, when the handler serves calls. Plans of three chips: a plan lists only the stages its chip needs, and every stage is synchronous or polled and bounded by a deadline. Most drivers declare one step, Start, that calls the driver's EnsureInitialized(); Identify and Configure happen inside the driver. The bno08x resets with Begin(cfg), synchronous, boots and links by calling Poll() until Ready(), polled, and configures with SetFeature operations until OpDone, polled. The se05x sets platform keys with SetPlatformKeys() (no I/O), opens the link, identifies and secures with Open(), synchronous and bounded by the link, and optionally verifies the lifecycle state. An optional stage is skipped, not failed, when the HAL supplies no pin, rail or key for it.

    Handler thread models¶

    Figure description and sources

    Two models, declared per bus, one above the other; callers on other tasks use one access API in both. Model O, the owner task, is the default for real-time buses: one real-time task, a kb::rtos::Thread, calls Service(now) at a fixed rate, steps the single-threaded cores of handlers A and B on BusDomain without a mutex (an owner check instead), publishes each step to a lock-free SeqlockSnapshot and drains a bounded command queue with completion. Other tasks read the latest snapshot with Latest() (a lock-free copy) or post a request with Request(cmd, timeout) and wait. Model G, the guarded facade, is for slow, sporadic devices: tasks X and Y each call Call(timeout, op) on a Guarded handler, C or D, which takes the handler lock and then, with a bounded wait (TryLockFor), the bus lock of BusDomain, which has a mutex, recovery and statistics. An interrupt service routine only sets event flags or notifies the owner task; it never calls a handler.

    Figure module: docs/diagrams/figures/handler-threading.py

    The layer stack¶

    Figure description and sources

    From top to bottom. The product application (control, protocols, safety layer) calls the board HAL: its facade and managers built on kb-hal-common, the board config (bus table, thread model per bus, chip list, pins) and the platform bind, which builds the port objects and sets the start-up order. The board HAL uses kb::handlers and picks one MCU port. In kb-core, kb::handlers (bindings, handler core, start-up pipeline, owner and guarded access) uses the driver of each chip and the interface contracts; kb::interfaces (C++20 concepts only, plus the host test port) rests on kb::rtos (the API, with the backends none, FreeRTOS and ThreadX), and kb::rtos rests on kb::utils (Status/Result, units, containers, CRC, seqlock). Each driver- is brand-free, has its own CI at level high and is pinned at release tags. The MCU port (port-esp32 in components/ports/esp32, its own CMake project; port-stm32 planned in its own repository) satisfies the interface contracts and touches the vendor SDK in its boundary files only; the RTOS backends touch the kernel in theirs. The vendor SDK, kernels and mbedTLS (ESP-IDF, STM32 HAL, FreeRTOS, ThreadX, mbedTLS) are SOUP: never analysed, never edited.

    MISRA C++:2023 scope¶

    Figure description and sources

    Four zones, from strongest claim to none. kb-core's own code under components/lib/** is claimed compliant with zero repository deviations: kb::utils and kb::interfaces (the contracts and the host port) in phase 1, the kb::rtos public API in phase 2, and kb::handlers with the bindings in phase 4. Boundary files, the files that touch vendor code, are compliant with recorded deviations: the RTOS backends' (components/lib/rtos/backends/freertos/_boundary.cpp, DEV-KBC-) and the ports' (components/ports/esp32/src/_boundary.cpp, DEV-KBP-, in their own records); the claim for kb-core's own code includes them. Each driver- at its pinned tag is covered by its own evidence, its own ru-misra run at level high. SOUP (ESP-IDF, STM32 HAL, FreeRTOS, ThreadX, mbedTLS) is out of scope, listed with versions, included with -isystem and never reported.

    The kb repository family¶

    Figure description and sources

    Consumers on top. A product organisation owns the product application and its board HAL, board-. The kokeb-labs organisation holds kb-core (utils, rtos, interfaces, handlers and the driver pins), kb-hal-common (shared HAL bases), the reference board HALs kb-board- and, planned, the configurator kb-configurator, an application template kb-app-template and the tested version sets kb-trains. The kokeb-labs-drivers organisation holds each driver- (one repository per chip) and each MCU port, port- (port-esp32, port-stm32). A board HAL builds on kb-hal-common and one port; both rest on kb-core, which pins the drivers. The configurator reads kb-core releases and fills the application template; the tested version sets list sets of kb-core. Only kb-core exists today; the other names are planned.

    Phase roadmap¶

    Figure description and sources

    Eight phases, M0 to M7, in order; there are no calendar dates, each phase ends on its exit criteria. M0 fixes decisions and guardrails: ADR-0006 to ADR-0013 recorded, and the include checker, poison build, symbol lint, preflight and CI skeleton green on empty parts. M1 to M3 deliver kb::utils v0.1, kb::rtos v0.2 and kb::interfaces v0.3: MISRA at level high with zero findings and zero deviations, the coverage floor, the mutation gate and clean fuzzing; kb::rtos adds the none and FreeRTOS backends, at-least delays, bounded locks, CRTP threads with statistics, approved boundary deviations and a clean TSan run; kb::interfaces adds concepts, a host port with fault injection, BusDomain, and conformance and compile-fail tests. M4 (v0.4) adds the ESP32 port with reviewed boundary files and the first three simple drivers bound and handled, integration, compat.yml, kb image check, configurator P1 and a bench run. M5 (v0.9 to v1.0) rolls out handlers for all drivers, simplest to hardest (bno08x, se05x and tmc9660 last), with start-up plans, both thread models, and health and recovery tests. M6 adds breadth: port-stm32, the ThreadX backend, tested version sets, and SBOM, CVE and licence evidence in the configurator (P2). M7 adds the generators: pin tables from board.yml, a project archive and HIL in scheduled CI.

    kb::rtos backends¶

    Figure description and sources

    One API, one seam, four backends. The kb::rtos API (Mutex, RecursiveMutex, Semaphore, Queue, EventFlags, Timer, Thread, CriticalSection in components/lib/rtos/inc) reaches a backend through kb::rtos::backend (backend.hpp), where each native object lives in opaque storage sized there and every backend static_asserts that it fits. The none backend is for host tests and bare-metal bring-up, with one context and a deterministic fake clock; the host backend (std::thread) runs PC tests with real threads and is never built for a target. FreeRTOS (the ESP32 default, any FreeRTOS target, static API only) and ThreadX (Eclipse ThreadX targets, one boundary file) reach their kernel through boundary files; the kernel is SOUP, from ESP-IDF or KB_FREERTOS_INCLUDE_DIRS for FreeRTOS, and from KB_THREADX_INCLUDE_DIRS or third_party/threadx for ThreadX. FreeRTOS and ThreadX also run their tests on fake kernels (tests/fakes) with exact ticks.

    The ThreadX backend¶

    Figure description and sources

    The kb::rtos API (Mutex, RecursiveMutex, Semaphore, Queue, EventFlags, Timer, Thread, CriticalSection) reaches the seam, kb::rtos::backend in backend.hpp. The ThreadX backend is two files: threadx_isr.cpp, where every FromIsr call is the same call with TX_NO_WAIT, and threadx_boundary.cpp, the only boundary file, which creates ThreadX objects (tx_*_create) on kb-owned control blocks and stacks. The kernel is SOUP and never edited; it comes from a product's copy (KB_THREADX_INCLUDE_DIRS, for STM32Cube or a vendor SDK) or from the pinned submodule third_party/threadx at a release tag, with KB_THREADX_PORT choosing cortex_m0, cortex_m4, cortex_m7 or linux. Tests run the boundary on a fake kernel in tests/fakes/threadx (contract and seam, exact ticks, kb_rtos_tests_threadx) and, on the pinned kernel's Linux port, as a threaded suite with priority inheritance (kb_rtos_tests_threadx_linux).

    The update path¶

    Figure description and sources

    From the top. kb outdated (exit 3 when a component can move), kb upgrade, or the configurator's Open an existing project view plan from the current lock, the catalogue and the image; the current versions come from the lock. kb-core moves first, then an extracted port, then each driver in name order. Each candidate must pass the driver gates in order (MCU family, kb_core_min, owner-task rule, bus kind in use); a newer version that fails is held back with the code of its first failing gate. The plan lists one row per component with the SemVer change, whether it breaks, and known vulnerabilities fixed and remaining. kb upgrade writes a new image and lock, the CMake files, the fetch script and kb-upgrade.md; the user then reviews the diff, runs sh kb-fetch.sh, builds and tests.
