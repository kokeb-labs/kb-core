    Handlers¶

    A handler binds one driver instance to one device on a bus, one configuration and a health record, and gives the HAL a small typed API. Every handler is built the same way: a binding (the driver's port over kb contracts, the error map, the start-up plan) and a handler class on the shared core. Decisions: ADR-0009 (thread models) and ADR-0010 (start-up pipeline); design: Handlers.

    The pieces¶

    Figure description and sources

    From the top. A HAL manager or application task calls an access facade with EnsureStarted, Request, Sample, Latest or Health; there is one facade per handler, chosen by the bus's thread model: OwnerAccess (request queue and a lock-free snapshot) or Guarded (handler lock, then bus lock). Only a facade can make the ServiceKey that the handler core needs, and the facade also owns the BusDomain of its bus, which holds one bus and its declared thread model. The core, HandlerCore of the handler, the driver, the snapshot, the command and the reply, holds the start-up plan runner (kStartupPlan), the health record and the snapshot (both seqlocks) and a liveness beat. It builds the driver in a std::optional; the driver reaches the bus through the binding's Port, driver hooks (I2cHooks, SpiHooks, UartHooks, AdcHooks, GpioHooks) over the kb::iface contract through which the HAL supplies its bus, pins and clock.

    Drawn from: docs/model/handler-pieces.graph.yml.

    Piece Header What it does
    HandlerCore common/handler_core.hpp Lifecycle, start-up runner, health, snapshot, recovery with backoff
    HealthTracker, HealthRecord common/health.hpp, common/types.hpp The one place health changes; a lock-free copy for any task
    BusDomain, BusHold common/bus_domain.hpp One bus and its declared thread model
    OwnerAccess, RequestChannel common/owner_access.hpp, common/request_channel.hpp Model O: the owner task services; other tasks post and wait
    Guarded common/guarded.hpp Model G: bounded handler lock, then bounded bus lock
    I2cHooks ... GpioHooks, HookTiming common/hooks.hpp Each driver hook once per bus kind: counters, failure recording, delays, clocks
    LivenessMonitor common/liveness.hpp Which handlers stopped beating, for a watchdog task
    Seqlock common/seqlock.hpp Single writer, many lock-free readers

    Lifecycle and health¶

    Figure description and sources

    Six states. A handler starts Unknown (constructed, no I/O). EnsureInitialized or StartStep moves it to Starting, which walks the declared stages, each bounded by its deadline; the last stage makes it Ready, a failing stage makes it Faulted, and a failed start leaves the driver destroyed so the next start begins again from the first stage. A failing call makes a Ready handler Degraded until the next call succeeds; fault_after failures in a row, or one fatal error (the chip reset or lost its state), make it Faulted. Recover() moves Faulted to Recovering with a backoff that doubles on each failure, and is refused after max_attempts; Recovering returns to Ready when the plan succeeds and to Faulted when it fails. Deinitialize() returns Ready or Faulted to Unknown. Only EnsureInitialized, StartStep, Deinitialize and Recover change the lifecycle: calls never start or restart the chip.

    Drawn from: docs/model/handler-health.state.yml.

    A call refused for the caller's own mistake (InvalidArgument) is recorded as the last error and counted in refused_calls, but does not change the state. A binding may say which failures are fatal (IsFatal) and which do not count (CountsAgainstHealth). On an owner bus, a successful periodic read clears the failures in a row, so failing commands alone reach fault_after only between reads; bindings whose commands matter more than their reads document a longer sample_period.

    Same caller API in both models¶

    Call Owner model (OwnerAccess) Guarded model (Guarded)
    EnsureStarted(timeout) Asks the owner task, waits for the plan's end Runs the plan under both locks
    Request(command, timeout) Posts to the bounded queue, waits for the reply (Busy, Timeout) Runs the command under both locks (Timeout, nothing sent)
    Sample(timeout) The owner reads now and publishes Reads now under both locks and publishes
    Latest(), Health(), Startup() Lock-free copies Lock-free copies
    RequestRecovery(timeout), Stop(timeout) On the owner task Under both locks

    Tests¶

    • components/lib/handlers/tests/: the core on the deterministic none backend, both facades, and real threads on the host backend (contention, lock timeouts, recovery storms, seqlock readers); compile-fail tests for a wrong facade, a wrong bus kind, Guarded over a chip that requires an owner, a missing ServiceKey and a plan out of order.
    • components/lib/handlers/fuzz/: the request queue against a model of its slot protocol.
    • tests/integration/<name>/: each binding drives its real driver over a kb contract backed by the driver's own chip model, in both thread models (owner only where the chip requires it).
    • tools/mutants/handlers.txt: a mutant per rule of ADR-0009 and ADR-0010 that a test must catch.
