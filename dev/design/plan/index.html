    Plan¶

    The design of kb-core in one page: what it is, the decisions taken, the phases and their exit criteria, and the risks. Detail is on the design pages (handlers, MCU ports and repositories, assurance, configurator, design rules) and in the decision records.

    Summary¶

    1. Shape. One repository, four parts (kb::utils, kb::rtos, kb::interfaces, kb::handlers), one version, drivers as submodules pinned to release or release-candidate tags. The board HAL sits above; applications use the HAL, kb::utils and kb::rtos only (architecture).
    2. Contracts. C++20 concepts only, no virtual functions; a short register of CRTP bases that carry real shared behaviour; run-time choice through type-erased *Ref values (ADR-0006).
    3. MCU ports. A separate layer from the first commit: components/ports/esp32/ is its own CMake project inside kb-core until the contracts settle, then kokeb-labs-drivers/port-esp32 (ADR-0007, ADR-0008). RTOS backends and the host test port stay in kb-core.
    4. Handlers. One driver, one bus-domain device, one configuration, a health record. A single-threaded core with one of two access facades declared per bus: an owner task with snapshots (default for real-time buses) or a lock-guarded facade (ADR-0009). Start-up is a plan of declared stages that also fits bno08x and se05x (ADR-0010).
    5. Assurance. Level high: CodeQL MISRA C++:2023 plus the compliance matrix; zero repository deviations above the boundary files. Drivers and handlers are not the safety layer; safety is a later option (ADR-0011).
    6. Releases. Each release records its own SHA and every pin in a release lock, with SBOM, CVE scan and licence report (ADR-0012).
    7. Configurator. A static site (GitHub Pages) to pick MCU, RTOS, drivers and handlers and download a repeatable, pinned project with its evidence (ADR-0013).

    Phases¶

    Each phase ends on its exit criteria, not a date.

    Figure description and sources

    Eight phases, M0 to M7, in order; there are no calendar dates, each phase ends on its exit criteria. M0 fixes decisions and guardrails: ADR-0006 to ADR-0013 recorded, and the include checker, poison build, symbol lint, preflight and CI skeleton green on empty parts. M1 to M3 deliver kb::utils v0.1, kb::rtos v0.2 and kb::interfaces v0.3: MISRA at level high with zero findings and zero deviations, the coverage floor, the mutation gate and clean fuzzing; kb::rtos adds the none and FreeRTOS backends, at-least delays, bounded locks, CRTP threads with statistics, approved boundary deviations and a clean TSan run; kb::interfaces adds concepts, a host port with fault injection, BusDomain, and conformance and compile-fail tests. M4 (v0.4) adds the ESP32 port with reviewed boundary files and the first three simple drivers bound and handled, integration, compat.yml, kb image check, configurator P1 and a bench run. M5 (v0.9 to v1.0) rolls out handlers for all drivers, simplest to hardest (bno08x, se05x and tmc9660 last), with start-up plans, both thread models, and health and recovery tests. M6 adds breadth: port-stm32, the ThreadX backend, tested version sets, and SBOM, CVE and licence evidence in the configurator (P2). M7 adds the generators: pin tables from board.yml, a project archive and HIL in scheduled CI.

    Risks¶

    Risk Likelihood Effect Mitigation
    Handler rollout for 23 drivers takes longer than everything before it High v1.0 slips Hook bases first; before v1.0 bind only what a board HAL needs
    Handbook and kb-core disagree (handbook ADR-0013 layout, ADR-0016 boundaries, handler.md start-up sentence) Medium Failed checks, rework Amend the handbook in M0 (see open items)
    A run-time choice is needed where no *Ref exists Medium Template bloat or a late API change Add the *Ref per contract when the first HAL needs it; reviewed like any contract change
    Template lint gaps waste CI runs High CI minutes Fix in the template before M1; preflight before every push
    Contract churn after the port is extracted Medium Two-repository pull requests Extract only at M4 exit
    Solo maintainer: independent review hard to staff High Process gap A separate independent review pass plus a recorded owner sign-off per part
    Static-initialisation and ISR-mask hazards on target Medium Boot wedge Constructors never touch the RTOS or hardware; a target smoke test that constructs every kb type statically
